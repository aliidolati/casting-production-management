## New-passport assignment compatibility fix — 2026-10-30

A new passport immediately creates MELT_PASSPORT_ENTRY. An older MySQL native ENUM or Hibernate-generated CHECK on tasks.task_type can reject that new code (1265/3819). The shared exception handler maps these integrity errors to the generic 409 "changed/conflicting information" message, so that message alone does not prove another person edited the passport. The original H2/Chrome run recreated a current schema and did not exercise this upgrade condition. This failure was reproduced on isolated MySQL 8.0.31; the user's deployed schema has not been queried, so its exact failing constraint remains unverified.

TaskTypeSchemaRepair now runs at startup on MySQL and conditionally converts a legacy native task_type ENUM to nullable VARCHAR(48). It removes only an enum-style, single-column task_type IN (...) CHECK that omits a current TaskType; mixed business checks and current enum checks are preserved. MySQL metadata charset introducers and escaped quotes are normalized before recognizing a check. No task rows, workflow state, assignment, approval, history or permissions are rewritten. V36__task_type_melt_compatibility.sql supplies the corresponding repeatable manual MySQL upgrade after the existing tasks/V35 baseline. This supersedes the earlier assumption below that the deployed task_type is necessarily unrestricted VARCHAR merely because JPA/V26 declare it.

The opt-in MeltTaskTypeMigrationMysqlTest uses only a fresh melt_tasktype_synthetic schema on a disposable loopback MySQL instance at port 13390; it never loads the application's default datasource. It reproduces both legacy failures, exercises V36 and startup repair twice apiece, checks both new melt codes, preserves null/legacy rows, and verifies that unrelated/mixed/current CHECKs still enforce their rules. Enable with -Dmelt.tasktype.mysql.enabled=true -Dtest=MeltTaskTypeMigrationMysqlTest test, and stop the helper afterward. Validation on 2026-10-30 passed **81 affected tests, zero failures/errors/skips**: this MySQL regression plus H2 melt workflow, passport, committed-transaction concurrency, task API and permission-seeding tests. No frontend assets changed. Production execution/deployment and the historical full migration chain remain unverified.

## Data and access

`MeltPassport` holds one shared furnace operation, UUID-based unique `MELT-...` number, date/furnace/ingot information, both decimal ingot weights and batches, process conditions, operator name, notes, and the independent magnesium inputs/result/time. The creator, editor, submitter, reviewer and return actor are copied from the authenticated account, including stable user IDs. The manually entered injection operator is a separate business field.

`MeltPassportPiece` stores piece membership and copied piece name/full project-row-piece reference. Its nullable unique `activePieceKey` prevents a piece being attached to two current passports. Entering CASTING again clears only that key; previous memberships, consumption and approvals remain visible from the piece. There is no automatic fabrication of approved passports for existing production records.

`MeltMaterial` has a stable ID and unique normalized name (Unicode normalization, Arabic/Persian kaf/yeh, whitespace/case normalization). An existing normalized name is returned instead of a duplicate. A concurrent insert conflict returns 409. Administrators may deactivate/reactivate catalog entries; there is no destructive catalog deletion. `MeltConsumption` copies material name/category and stores the entered decimal quantity/unit, batch, time and notes. It also stores a normalized base quantity: G/KG/TON -> KG, ML/L -> L, COUNT -> COUNT. Different dimensions are never summed. Inactive materials already used by a draft remain editable; inactive materials cannot be newly attached.

`MeltCheck` stores the six fixed control kinds with UNCHECKED/ACCEPTED/REJECTED and a note. Defaults are UNCHECKED. `MeltPassportEvent` records every create, update, calculation and workflow decision with account identity, timestamp and return reason. Ordinary events record operations/status changes; ADMIN_CORRECTED events additionally retain full before/after business snapshots in nullable old_values/new_values columns. Legacy events have no fabricated snapshots.

Piece APIs currently allow every authenticated active user to view pieces. The module follows that existing access scope; it does not invent project assignments. Draft creation and edits require all selected pieces to be unarchived and in CASTING. Reviewer authority is checked inside the transactional service: ADMIN or `APPROVE_MELT_PASSPORT`. The permission is exposed through the existing permission catalog/user editor and is deliberately absent from default operator permissions and startup grants. As of 2026-10-22, the general register and consumption report require ADMIN or `VIEW_DASHBOARD` in the service as well as the UI. Pending-review filtering additionally requires reviewer authority. Piece-specific history, reading, drafting and reviewing remain independent of the dashboard permission: an approver without dashboard access can review from a piece profile.

## Workflow and stage integrity

`DRAFT -> PENDING_APPROVAL -> APPROVED`, or `PENDING_APPROVAL -> NEEDS_CORRECTION -> PENDING_APPROVAL`.

Incomplete headers/process fields and selected material rows with an empty quantity can be saved as drafts. The submission contract requires date, integer furnace number, ingot type, both nonnegative weights with a positive sum, injection operator, and all six controls reviewed. Rejected controls require explanations; acceptance is ultimately the reviewer's decision. Any entered consumption quantity must be positive on submission. These are implementation choices for the unspecified essential-field set; other process measurements remain optional. If any magnesium input is entered, all six must be completed and explicitly calculated before submission. Leaving all six empty keeps the optional calculator unused. Negative calculated results remain visible for review.

Both pending and approved records are immutable through the ordinary edit/calculation endpoints, including for administrators. A separate correction endpoint permits ADMIN to amend approved business data with an audit (see below). Returning a pending record requires a nonblank reason. Repeated submissions/returns retain their individual audit events as well as the latest actor/time fields. There is no approved-passport reopen/cancel operation.

`MeltPassportService.approve` locks the passport and all members in stable UUID order, checks the client version and pending state, rechecks every piece's archive/stage/active membership, then updates approval and advances all members in one transaction. `PieceService.advanceByMeltApproval` obtains the destination/substage from `StageTransitionPolicy.forwardMove`, rather than naming the next stage in this module. Existing actual CASTING process dates are preserved; if absent, the melt date supplies that date. Central movement still creates stage/substage history, saves outgoing dates, and clears the incoming current process date.

`MeltPassportGate` is called by the central `PieceService.applyStageChange` and the separate welding dispatch entry. Every departure from CASTING—including dated advance, generic/bulk moves, admin corrections, scrap and trusted tensile/welding routes—requires an approved active passport. The gate does not change normal rules for pieces already at other stages. Legacy startup remapping of old radiography codes is unrelated and unchanged.

Passports use `@Version` plus a pessimistic decision lock. Pieces now also have `@Version` (existing rows default to 0), so an older concurrent stage/archive write cannot overwrite the approval move. A decision failure rolls back approval, all member movements, dates, histories and events; this module writes no files. Stale versions/integrity conflicts return 409. Existing radiography/workflow guards remain active.

## Calculations

Server calculations use `BigDecimal`. Weight percentages are returned with four decimal places; a zero total returns null. Browser percentages are display previews and never accepted as authoritative inputs.

The exact independent expression is:

```text
(0.32 - Mg + (T_rotary * 0.2) + ((T_610 + T_ar) * B)) * w * 10 * 1.1
```

No weight, process duration or other form field populates these six inputs. New inputs are empty; null is distinct from zero. Calculation is an explicit POST against the saved inputs. Changing any input clears the saved result/time and immediately marks the displayed result stale. Result storage uses DECIMAL(38,12), with rounding only at the final result. Negative values are never clamped. Formula-input/result units remain unspecified, as requested; no units or coefficients were inferred from the PDF. There is no primary-ingot magnesium calculator.

The three T symbols use a capital T with lowercase `rotary` / `ar` or `610` as HTML subscripts in both labels and the displayed formula. These are fixed, accessible LTR labels; API keys `rotary`, `at610`, `ar`, coefficients and calculation semantics are unchanged.

The calculator grid itself is LTR, so visual and native Tab order both follow Mg, T_rotary, T_610, T_ar, B, w. Responsive rows wrap in that same order; the rest of the form remains RTL.

## Approved ADMIN corrections

`POST /api/melt-passports/{id}/corrections` accepts `{data: MeltPassportRequest, reason: string|null, calculateMagnesium: boolean}`; version is required inside data and reason is optional/max 2000 characters. `correctable` is true only for an authenticated active ADMIN reading an APPROVED passport. `editable` keeps its existing draft/correction semantics, so historical approved records do not hide the new-cycle action.

The transactional service checks ADMIN before mutation (403 for other roles, even with approval permission), locks the passport and checks version (409 if stale), requires APPROVED, and compares the exact member ID set (duplicates/additions/removals fail). It updates business fields, material consumption and controls without checking current piece stage/archive or changing any member/active key. Existing approval and submission identity/time, stage/substage histories and actual process dates are preserved. A changed melt date affects the passport only; there is no repeat approval or movement. An earlier approved cycle is correctable independently of a later draft/active passport.

A detached candidate receives the proposed fields and existing legacy clock value/material snapshots, then undergoes the same submission completeness rules. Changed magnesium inputs invalidate the candidate's result; unless all six are empty, saving requires explicit calculateMagnesium=true to calculate and persist the corrected data/result together. Partial inputs fail without any saved correction; negative results retain existing behavior. Calculation changes are audited within ADMIN_CORRECTED rather than a second transaction/event.

`MeltPassportAudit` serializes canonical business snapshots with full decimal precision, excluding recursive events, permission flags and generated material-row IDs. Unchanged values (including decimal scale-only changes) return the original response/version without replacing rows or adding history. Actual changes update the versioned parent and add ADMIN_CORRECTED with copied actor ID/name, time, optional reason and old/new values in the same transaction. Failure rolls everything back. Concurrent corrections using one version yield one success and one conflict.

The UI starts approved records read-only, exposes an ADMIN correction button, and keeps pieces read-only in correction mode. It offers cancel, save, optional reason and explicit calculate-and-save; submit/review operations are absent. Errors preserve entered values and reason. History shows escaped old/new field values with Persian labels; old events render normally without a changes table. Consumption reports use the corrected current values; earlier values remain in the audit.

## Process clock and material category compatibility

`process.timeAt610Clock` is an optional `LocalTime` with a strict JSON `HH:mm` contract (24-hour, minute precision); its nullable column is `time_at610_clock TIME(6)`. The process form uses a native time input with a 60-second step. The native chooser may render AM/PM according to browser/system locale, while its value and API payload are always 24-hour `HH:mm`. Null clears only the new clock field. Invalid clock strings return the existing localized 400 response and floating error feedback without replacing the user's form.

The old numeric `process.timeAt610` / `time_at610 DECIMAL(24,8)` has no established clock conversion. It is response-only in JSON, never taken from client writes or converted, and is displayed as «مقدار قدیمی» when present. The process mapper preserves it from the existing entity, including when an update omits/nulls the whole process. Approved/pending passports remain immutable. The new process clock has no relationship to the numeric magnesium input `at610` and does not invalidate a saved magnesium result.

Only the material-creation category suggestion changes from «اصلاح‌کننده» to «کاورال». Categories remain free text. Existing catalog categories, consumption snapshots and reports keep their stored names; no display alias, catalog rewrite or data migration renames them.

## API and interface

All routes are under `/api/melt-passports`; existing JWT authentication applies.

| Route | Use |
|---|---|
| `GET /today` | Default ISO date from the project's system-zone Clock |
| `POST /`, `GET /{id}`, `PUT /{id}` | Create/read/update; write contracts include `version` |
| `POST /{id}/submit`, `/approve`, `/return` | Workflow decisions with expected version; return requires reason |
| `POST /{id}/calculate-magnesium` | Explicit calculation of the saved independent inputs |
| `POST /{id}/corrections` | ADMIN-only audited correction of approved business data; optional atomic magnesium calculation |
| `GET /piece/{pieceId}` | All passports associated with a piece, including previous casting cycles |
| `GET /candidates?q=...` | Available unarchived CASTING pieces, at most 100 results; localized numeric piece number, full reference, partial piece name or project code |
| `GET /ingot-types` | Previously entered ingot names; the form also accepts new names |
| `GET/POST /materials`, `PATCH /materials/{id}/active?active=...` | Material catalog and admin activation |
| `GET /` | Requires dashboard access; paginated `PageResponse`: date range, furnace, piece ID, ingot type, material ID, operator, status |
| `GET /consumption` | Requires dashboard access; the same filters; approved status by default |

Consumption aggregates passport rows and their materials once, using EXISTS for piece/material filters. Linking two pieces never multiplies a melt's consumption. Non-approved status filters explicitly request provisional data; missing draft quantities do not contribute. Querying large consumption date ranges currently loads matching passports/materials in memory; no historical production-volume performance benchmark was performed.

The profile has a dedicated document/crucible SVG icon beside the radiography/tensile/heat icons, with a count badge and latest status. It opens the newest passport at any production stage; a selector inside the form exposes previous casting cycles. With no records, an active CASTING piece opens a new preselected draft; other stages show a floating no-record warning. A CASTING re-entry with only earlier approved history exposes a new-cycle button. The old profile list and general header button were removed. «داشبورد ← گزارش‌ها ← شناسنامه‌های ذوب» opens the register with filters, consumption and admin catalog activation; reviewers with dashboard access start with pending approval.

The shared form retains all four sections, Jalali picker and ISO API dates. Desktop inputs are 32px high with a four-column grid and reduced gaps/padding; narrow layouts use one/two columns and 40px inputs. The material table scrolls inside its wrapper. Errors throughout the module use an escaped top-position toast above the dialog for six seconds, with no bottom error box or forced scrolling. Magnesium input changes warn once per calculation and clear the visible valid-result state; negative calculations also raise a warning. Existing status/correction/result information stays in the form. Failed requests preserve typed values, obsolete form responses are ignored, and duplicate search errors are coalesced. During a mutation, enabled form controls (including the history selector) are temporarily disabled, then restored on failure; this prevents save/history-selection races. Shared `showToast` now accepts optional `{position, durationMs}` and replaces its previous timeout; unchanged two-argument callers retain their default bottom/three-second behavior. `apiRequest` adds `status`/`errors` metadata to thrown errors so validation details can be shown as plain text.

## Candidate search and MySQL collation

The former full-reference `LOWER(CONCAT(project.code, '-', CAST(row AS CHAR), '-', CAST(piece AS CHAR))) LIKE ...` can derive an unresolved binary collation when the project column and connection collations differ. The reported MySQL error 1267 was reproduced on an independent MySQL 8.0.31 with a `utf8mb4_unicode_ci` project code and `utf8mb4_0900_ai_ci` connection.

`MeltCandidateSearch` now parses numeric input and full references in Java. It splits full references from the right to preserve hyphens in project codes and accepts Persian/Arabic digits in the numeric suffixes. The repository compares numeric columns directly and uses separate bound text predicates for name/project code, with literal `%`/`_` escaping. No SQL CAST/CONCAT is used in the candidate query, no collation/schema changes are required for the application, and eligibility checks, deterministic order and the 100-result database limit remain in place. Numeric-only input is an exact piece number; an oversized number returns no candidates instead of falling back to text matching. An incomplete reference is treated as text while typing.
