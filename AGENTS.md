# Development rules

- Start with `docs/ai-context/PROJECT_OVERVIEW.md` and the relevant architecture/workflow document. Verify source when documentation and comments disagree.
- This is one Spring Boot/Maven application (`com.factory.productmanager`) serving classic JavaScript from `src/main/resources/static/`; there is no frontend package/build pipeline.
- Keep controllers thin, HTTP contracts in DTOs, business mutations in transactional services, persistence in repositories, and resource authorization on the server.
- Route production changes through `PieceService` and `StageTransitionPolicy`. Preserve history, actual process dates, archive rules, and differences between dated advance, generic/bulk movement, admin correction and trusted tensile/welding routes.
- Use radiography workflow services for approvals and workflow-task transitions. Check report, defect, template and generic task entry paths; their current guards differ. Preserve snapshots/signature copies and open-workflow uniqueness.
- Use `TaskLookup`/`TaskAccessPolicy` for task visibility and nested resource ownership. Preserve invisible-resource 404 versus visible-but-forbidden 403.
- Preserve `ADMIN`/`OPERATOR`, persisted enum/permission codes and legacy aliases. `MANAGE_PIECE_ASSIGNMENT` controls tensile test entry. Test startup seeding when changing permissions.
- Use BigDecimal for tensile values; distinguish missing thresholds/values from failures. Test approval, correction, disposition, aging and resulting piece movement together.
- Do not start the application or run SQL against the default datasource for exploration. An explicitly user-authorized read-only inspection/backup is allowed; never run source DDL/DML or restore without separate approval. Use isolated synthetic-data databases and upload storage for tests; startup can mutate schema, permissions and records.
- Before schema changes, reconcile JPA, SQL migrations and startup repair classes. Flyway properties do not prove execution; the SQL chain is incomplete for tasks. Never assume H2 tests validate MySQL migrations.
- Do not assume database rollback undoes file changes or `@Transactional` applies to same-instance calls. Preserve approval-file rollback cleanup and evaluate concurrency explicitly; inspect each entity's version/locking strategy.
- Keep Persian text UTF-8, RTL/Jalali behavior, ISO API dates, classic-script order, DOM IDs and escaping. Add API wrappers in `api.js`; update matching `index.html` asset `?v=` values when JS/CSS changes.
- Run affected existing Maven tests; use `node --check` for edited JS and relevant browser smoke checks. Add focused regression tests for business/security changes. Tests use H2 and `target/test-uploads`; never redirect them to production.
- Never copy secrets, sensitive configuration values, raw credential-bearing logs, signatures, uploaded drawings or production records into documentation/issues. Do not treat `target/`, `uploads/` or IDE files as source.
- Update relevant `docs/ai-context` files when architecture/workflows change. Clearly label unverified assumptions and report validation limits.

## Architecture, compatibility and change scope

- Keep changes minimal and tied to the requested behavior. Before broad edits, inspect the affected callers, services, DTOs, entities, tests and dependencies. Preserve every existing capability unless removal is explicitly requested.
- Backend: one Spring Boot 4.1 application, Java target 17, Maven wrapper, package `com.factory.productmanager`. Source is in `src/main/java`; dependencies/plugins are in `pom.xml`; test resources and synthetic fixtures are in `src/test`.
- Frontend: same-origin HTML/CSS and classic JavaScript in `src/main/resources/static`, with bundled fonts/images, Persian RTL UI and Jalali display dates. No separate frontend repository, npm build or JS framework exists. Match the current visual design and responsive behavior when UI changes are requested.
- HTTP compatibility: inspect controllers, DTOs and `static/js/api.js` together. Preserve routes, verbs, field names, validation, ISO dates, status codes, permission checks and response shapes unless a contract change is explicitly requested. Test affected clients as well as server contracts.
- Entity/database compatibility: inspect JPA, all related migrations and startup repairs before changing fields, indexes, enum codes or relationships. Add a reviewed, data-preserving migration for schema changes and focused MySQL upgrade tests. Never use `ddl-auto` to claim migration correctness, turn on the incomplete Flyway chain blindly, or perform destructive operations on the main database.
- Build without starting the application: `./mvnw -B -ntp -DskipTests package` (Windows: `.\mvnw.cmd -B -ntp -DskipTests package`). Run the affected existing tests before committing; use the Cloud/CI commands below. Do not launch the default datasource for build verification.
- Runtime secrets stay outside Git. `.env.example` documents variable names only; Spring Boot does not automatically load `.env`. Use environment variables or an external private properties file. Never commit a local workaround containing datasource or JWT literals.
- Keep Backend and Frontend together. The initial local inspection found no pre-existing Git repository or nested repositories. For normal Cloud development use a task branch and a pull request; review diff and CI before merging. Never force-push, rewrite existing history, delete a repository, or publish private data without explicit authorization. Initial source publication requires the user's separate pre-push approval.

## Cloud and CI database tests

- Read `docs/ai-context/CLOUD_TESTING.md`, `DATABASE_STRUCTURE.md` and `MYSQL_SCHEMA_INVENTORY.md` before changing test/schema infrastructure.
- Use JDK 17+ and the Maven wrapper. Cloud setup: `bash scripts/codex-setup.sh`. Fast tests: `bash scripts/test-backend.sh fast` (unit + Spring Boot/H2, no runtime secrets or MySQL needed).
- Real MySQL: `bash scripts/test-backend.sh mysql`, or `./mvnw -B -ntp -Pmysql-it -DskipUnitTests=true verify`. Failsafe runs `*Mysql*Test`; Docker is required by default. Missing Docker must fail this job, not silently mark MySQL tests passed.
- `.github/workflows/backend-tests.yml` runs separate fast and MySQL jobs on GitHub-hosted Ubuntu. No laptop, source database, production secrets or uploaded files are needed. Do not use a runner on the user's laptop.
- MySQL tests may connect ONLY through `src/test/java/.../support/IsolatedMysql.java`. It starts its own Testcontainers MySQL 8.0.31 with random credentials/port and fresh synthetic schemas. Never accept externally supplied JDBC URLs as a fallback. Do not enable container reuse.
- Explicit native fallback: `-Pmysql-it -DskipUnitTests=true -Dmysql.tests.runtime=native -Dmysql.native.bin=/absolute/path/to/mysqld verify`. This creates an owned MySQL 8.0 process with a new `target/` datadir and random loopback port; it never uses a system service or the default datasource. Keep native logs/data ignored.
- Existing opt-in MySQL regression flags are set by the Maven profile. Do not revive their former fixed localhost URLs/credentials. Test uploads stay under `target/test-uploads/mysql/`.
- `src/test/resources/db/mysql/schema-synthetic.sql` is a reviewed, record-free structural fixture of the inspected local schema. Import only into an empty owned synthetic schema. `SchemaBaselineMysqlIntegrationTest` loads it before JPA `validate`; other MySQL API tests use Hibernate `create-only`. None of these prove that the incomplete V1–V36 migration chain bootstraps a database.
- New schema changes require reconciling entity mappings, migration scripts, startup repairs and this structural fixture, plus focused MySQL regressions. Do not add the Boot Flyway starter or enable automatic migration against existing databases as part of routine test setup.
- Runtime datasource and JWT values are external (`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`, `JWT_SECRET`). An empty runtime database additionally requires `APP_BOOTSTRAP_ADMIN_PASSWORD`; never restore a hardcoded bootstrap password or log credentials. Test-only fixtures are separate.
- Actual backups and private runtime properties belong outside the repository. Never import production records, password hashes, signatures, drawings, copied names, audit JSON or snapshots into tests. Generate synthetic fixtures instead. Never upload private exports, uploads, raw logs or full `target/` as CI artifacts.
